## 2. 离线原理

游戏是 Unity IL2CPP + Addressables,DMM 平台登录。StoryViewer 插件(BepInEx + Harmony)做四件事:

1. **假 DMM 凭证**(`OfflineAuth`):跳过登录,直接进游戏。
2. **本机假 API 服务器**(`OfflineApi`,端口 18923):应答主数据与游戏 API 请求。
3. **资源重定向**(`RedirectAssetServer` + `ServeCachedBundles`):把 Addressables
   的 catalog/bundle 请求指到本机,由插件从客户端自带的 `_Data\Caches\<bundleName>\<hash>\__data`
   取用。
4. **本地内容**:剧情浏览 UI(F7)、剧情内跳过(F8)、解锁补丁(资料室全开放)、
   隐藏联网入口(商店/抽卡等)、错误弹窗与教学门禁的绕过。

**关键约束:未命中的 bundle 直接回 404,不回流官方 CDN。** 因此

- 离线包必须带**完整**缓存,不能做瘦身包;
- `Caches` 顶层条目数 < 10000 一律视为不完整(自检会红灯);
- 日志里出现 `→ 404` 行 = 有资源没命中缓存。

### 2.1 身份隔离(app.info)

- `ドットアビスX_Data\app.info` 两行:公司名 `EXNOA LLC.`、产品名 `ドットアビスX`。产品名会被
  **打包与修复改成 `ドットアビスX_offline`**,于是 LocalLow 存档、缓存、注册表与
  在线版完全分开(`LocalLow\EXNOA LLC_\ドットアビスX_offline\`),两边同时安装互不干扰。
- 备份 `app.info.bak_original` 只存在于开发机,**不进包**(打包会删掉)。
- 这是唯一允许修改的游戏本体文件;任何其它本体文件都必须走更新通道的 `client_body`。

### 2.2 catalog 与 LocalLow 播种(新机器首启的关键)

- 插件原本只从 `LocalLow\...\com.unity.addressables\*.bin` 读 catalog(取最近修改一份)。
  新机器 LocalLow 是空的 → 首启必失败。修法分三层:
  1. **包内种子**:`BepInEx\plugins\StoryViewer\catalog_seed\catalog_1.bin` + `.bin.hash`;
  2. **插件回退**(0.7.17 起):`ResolveCatalogFiles()` 优先种子目录,再回退 LocalLow;
  3. **启动器播种**:首次准备/修复/开始游戏前,把种子同步到
     `LocalLow\...\ドットアビスX_offline\com.unity.addressables\`(哈希一致则跳过)。
- `local_low_seed\AbsfRuntimeConfig.dat`:新机器存档目录缺该文件时补种(只补缺失、绝不覆盖)。
  它是游戏运行期写出的配置,缺省时游戏通常能自行重建,此播种是防御性措施。
- `local_low_seed\DownloadCache\*.dat`:`MasterDataStore.DownloadFirstAsync` 首次下载后
  写入的主数据磁盘缓存。新版主数据不在 Addressables Caches 或通用 API JSON 中;
  缺它会出现 `MBuildings not found` 等主数据缺失错误,因此完整包必须从在线
  `LocalLow\EXNOA LLC_\ドットアビスX\DownloadCache` 原样带入并在首启补种。增量更新
  通过专用 `master_data.zip` 投递同一目录;主数据缓存可按大小/MD5 替换,其它文件仍不覆盖。
- 更新通道也带 catalog(附件 `catalog_1.bin` + `.bin.hash`):启动器下载后写入包内种子
  目录,并立即重新播种 LocalLow。

`stories.json`(剧情索引)与 `previews/`(封面)是构建期从缓存导出、由插件读取的静态数据;
它们的格式与导出流程见仓库根 `README.md` 的导出工具一节。

## 3. 插件开发与部署

```powershell
# 编译 + 部署到 client\(版本号在 StoryViewer.csproj)
pwsh -File tools\client-mod\build.ps1

# 配置档:offline(默认)/ online-ref(在线抓包对照,需 VPN 与新鲜 DMM 凭证)
pwsh -File tools\client-mod\set-profile.ps1 show
pwsh -File tools\client-mod\set-profile.ps1 offline
pwsh -File tools\client-mod\set-profile.ps1 online-ref
```

- 插件版本以 DLL 的 `ProductVersion` 为准(csproj `<Version>`);打包时会把配置头注释
  与 `offline_version.json` 一并刷成该版本。
- 玩家默认档在打包时生成:**离线键全为离线值**,并把 `LogPatches`/`SkipDebug` 关掉
  (`ErrorPopupLog` 保持开,便于支持)。

## 4. 启动器

- 源码:`tools/launcher/dotabyss_launcher.py`(tkinter,无第三方依赖)+ 共享逻辑
  `tools/launcher/dotabyss_offline_core.py`;配色取自游戏内 StoryViewer 面板,保持同一视觉风格。
- 冻结:`pwsh -File tools\launcher\freeze_launcher.ps1`
  - 先结束**同目录**残留的启动器进程(onefile 会留下子进程,持有 exe 会让 PyInstaller 报 WinError 5),
    再 PyInstaller onefile 到 `client\`,最后跑一次 `--smoke` 冒烟。
- 功能:开始游戏 / 更新 / 高级(自检 · 索引探针 · 修复 · 打开日志)。
- 所有界面改动都经**队列**回主线程(`__BTN__` 改按钮文案、`__QUIT__` 关窗);
  后台线程不直接碰 Tk(踩过 Tcl_AsyncDelete 崩溃)。
- **首次准备**:`offline_version.json` 的 `first_ready=false` 时自动执行一次
  安全修复(解除 Zone.Identifier、重写离线配置、设置离线身份、播种 catalog/附属种子、
  归档超大日志)+ 全项自检,然后写 `first_ready=true`。
- **启动静默检查**:窗口起来后台查一次 latest Release,只改按钮文案
  (「有更新」/「需重装」),不打扰、不阻塞。版本号相同也会按本地记录摘要和主数据种子
  做轻量就绪检查;缺失或不符时提示点「更新」补齐,不会扫描 430 MB 的本体/素材文件。
  顶栏只显示插件短版本,完整版本(含 source revision)写入启动日志。
- **更新顺序**(`_do_update`):基线门禁 → 安全修复 → `client_body` → `caches_added` →
  `master_data` → catalog → stories → previews → 插件 DLL → 玩家文档 → 启动器。
  **基线优先于版本号裁决**:基线不一致直接拒绝并要求重装完整包;版本号相同也会核对
  Release 已声明的产物,缺失或 MD5 不符时继续修复。
- **自替换**:更新启动器本体时把新 exe 写成 `.new`,退出后由分离的 cmd 替换并重启;
  若上次替换没完成,启动时用 `pending_launcher_swap` 兜底(再点一次启动器即可完成)。
- **自测口**(开发用,不写进玩家文档):
  - `--release-dir <目录>`:把网络取数映射到本地发布目录(`api.github.com` → `release.json`),
    用真实发布资产跑离线演练;
  - `--auto-update <输出文件>`:自动跑一次更新并把结果(`OK` / `OK-UPTODATE` /
    `BLOCKED-BASELINE` / `FAIL`)与日志尾巴写到文件;
  - `--smoke <输出文件>`:窗口起来即写 `PASS`。
- 单元测试:`test_offline_core.py`(108 项)、`test_launcher_update.py`(36 项)、
  `test_pack_tools.py`(11 项)。

## 5. 打包与交付

```powershell
# 完整包(复制 + 生成 + 校验;--zip 出压缩包;--repo owner/name 写更新仓库)
D:\Python\python.exe tools\launcher\build_full_pack.py --zip --repo owner/name

# 重发同一基线(不换基线时显式指定):
D:\Python\python.exe tools\launcher\build_full_pack.py --baseline 20260924

# GitHub 更新附件(见 docs\GitHub更新流程.md;--caches-since 产素材增量)
D:\Python\python.exe tools\launcher\build_github_pack.py --version 20260925 --notes "..."
D:\Python\python.exe tools\launcher\build_github_pack.py --version 20260925 --caches-since dist\旧包目录
```

- 完整包会**排除**开发产物:`BepInEx\capture\`、`StoryViewer\shots\`、`*.log`、`*.bak*`、
  `*.py/*.pdb/*.new`、`update_*.zip`、以及需要重新生成的 `dotabyss.storyviewer.cfg`、
  `offline_version.json`、`launcher.json`。
- 生成物:玩家默认配置、`offline_version.json`(`version`=打包日、`baseline`=基线、
  `channel`、catalog 摘要、`first_ready=false`)、`launcher.json`(更新仓库)、
  玩家文档与 `check_health.bat`、离线身份、`catalog_seed\`、`local_low_seed\`。
- `baseline` 是**冻结的基线包日期**:新完整包可以升 `version`,但同一代基线内不要改
  `baseline`;换基线 = 声明"必须重装完整包"。
- 校验不过会 `[ABORT]`,**不要交付未通过校验的目录**。

## 8. 已知坑与教训(务必遵守)

- **不要给高频方法挂 Harmony detour**,尤其参数里带 IL2CPP 对象/值类型状态机的
  (0.7.14 之前的致命 AV,随机崩溃)。F8 跳过现在的做法是:按键时
  `Resources.FindObjectsOfTypeAll` 实时找存活 `TopScene` 实例,直调 `OnSkipExec()`
  ——不打补丁、不缓存引用。
- `ViewerBehaviour` 的**实例方法里禁止捕获本地函数/`ref`/`out`**(IL2CPP 托管边界会炸);
  静态方法可以。
- AbyssMod 是另一个可能崩溃源。怀疑崩溃归属时,把 `StoryViewer.dll` 改名 `.bak`
  再跑一轮做隔离。
- **`cmd /c` 含引号路径的脚本必须用 `subprocess.Popen(script, shell=True)`**:
  argv 列表形式会被 Python 的 `list2cmdline` 把内层引号转义成 `\"`,cmd.exe 不认,
  替换脚本**静默失败**(2026-09-24 实测,启动器自替换因此卡住)。回归测试见
  `test_offline_core.py::LauncherReplaceCmdTest`。
- 后台线程禁止直接操作 Tk 控件(含 `root.after`);一律走队列,主线程处理。
  自测口同理(曾经的 Tcl_AsyncDelete 崩溃)。
- `check_health.bat` 里**不要用 `for %%F in ("%GAMEDIR%\*_Data\app.info")`**:
  cmd 的 `for` 不展开目录段通配;用先算好的 `DATADIR` 变量拼路径。
- 打包时 catalog 种子目录必须**先清空再写入且不写 `.bak_*`**,否则"无开发产物泄漏"
  校验会拦下(这是有意设计的守卫)。
- 控制台是 GBK,输出乱码先 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`。
- 工具里**不要启动游戏或 GUI 常驻程序**(会挂起);启动器冒烟/自测是短命进程,可以。
- `offline-api.log` 等运行期日志永远不进包(`*.log` 已在排除列表)。

## 9. 诊断日志收集与回传(取证)

玩家机黑屏/异常时,把运行时日志回收分析。**双端分工**:插件负责写日志
(`BepInEx\LogOutput.log`、`offline-api.log`),启动器负责**收集→打包→上传**。

### 9.1 客户端(`tools/launcher/dotabyss_offline_core.py`)
- `collect_diagnostics(game_dir)`:收集日志与环境信息,产出 `diagnostics\dotabyss-diag-<时间>.zip`。
  超大日志保留**头 2MB + 尾**(带截断标记,开机崩溃签名不被裁掉);并从开机段抽**「崩溃签名」**
  (`aa/runtime.json`、`TextDataProvider`、`BitConverter`、`InitializeAsync` 等)写进 `diag_summary.txt`,
  免解压即可一眼定位。
- **诊断包内容清单**(`zip 内路径` ← 来源):`diag/diag_summary.txt`(摘要:离线包版本/app.info/
  配置离线档与 DiagAssets·ApiPort/Caches 目录数与字节/资源命中统计/health_check/index_probe/崩溃签名)、
  `diag/logs/*`(BepInEx 下 `LogOutput.log` 等日志)、`diag/config/*.cfg`(BepInEx\config 全部)、
  `diag/offline_version.json`、`diag/app.info`、`diag/launcher.json`(仅 `github_repo`)、`diag/plugin/stories.json`。
  **故意不含**:服务器端点(IP/令牌/隐身路径只内建在 exe 里、不进包也不进摘要)、游戏存档、玩家隐私文件。
- `upload_diagnostics(game_dir, zip)`:POST `multipart/form-data`,字段 `file`=zip、`summary`=摘要纯文本;
  返回 `skipped/ok/error`。**未配端点时只保留本地 zip 并跳过,绝不猜端点。**
- 端点解析优先级(`_diag_upload_target`):环境变量 `DOTABYSS_DIAG_UPLOAD_URL`/`_TOKEN`
  → `launcher.json` 明文 `diag_upload_url`/`diag_upload_token` → 隐身字段 **`diag_endpoint`**
  (base64 的 `url\ntoken`,由 `_diag_encode_endpoint`/`_diag_decode_endpoint` 编解码)
  → **内建默认 `_DIAG_EMBED_B64`**(冻结进启动器 exe 的兜底,见 §9.4b;老玩家 `launcher.json` 无端点也能回传)。

### 9.2 启动器 UI(`dotabyss_launcher.py`)
「收集日志」→ `run_diag`:收集→上传;当结果为 `skipped`/`error` 时**自动打开 `diagnostics\` 目录**
并提示手动发网盘/Discord(大陆可达性兜底,始终保留)。

### 9.3 接收端
现网用**自建服务器**(`tools/diag-server/`,Node 零依赖 + systemd `dotabyss-diag` + 低权用户),
加固:非 `SECRET_PATH` 一律 404、`Bearer` 令牌、按 IP 限速、并发上限、64MB 上限、防火墙 SYN 限速。
**真实 IP/端口/令牌/隐身路径只存服务器 `/etc/dotabyss-diag.env`(600),不进仓库。** 部署/运维/回滚
详见 [`tools/diag-server/DEPLOY.md`](../tools/diag-server/DEPLOY.md)。`tools/diag-worker/`(Cloudflare Worker+R2)
保留为备选,**同一 multipart 契约**,客户端换 `diag_upload_url` 即切换。

### 9.4 打进随包 launcher.json(机密不进 Git)
构建前设环境变量,`build_full_pack.write_version_and_repo` 会把端点 **base64 编码**成 `diag_endpoint`
写入生成的 `launcher.json`(真实 IP/令牌既不进 Git,也不以明文出现在包里):
```powershell
$env:DOTABYSS_DIAG_UPLOAD_URL   = "http://<服务器>:<端口>/<隐身路径>"
$env:DOTABYSS_DIAG_UPLOAD_TOKEN = "<令牌>"
D:\Python\python.exe tools\launcher\build_full_pack.py --zip --repo owner/name
```
不设这两个 env 则 `launcher.json` 不含 `diag_endpoint`(回传关闭,行为向后兼容)。

### 9.4b 内建默认端点(重冻启动器,面向老玩家)
增量更新通道**不投递 `launcher.json`**(它是启动器自举配置,只存 `github_repo`),所以老玩家的
`launcher.json` 永远没有 `diag_endpoint`。为让老玩家**仅更新启动器**就能回传,冻结时把端点
烘进 exe 作最后兜底(明文仍不进 Git):
```powershell
$env:DOTABYSS_DIAG_UPLOAD_URL   = "http://<服务器>:<端口>/<隐身路径>"
$env:DOTABYSS_DIAG_UPLOAD_TOKEN = "<令牌>"
pwsh -File tools\launcher\freeze_launcher.ps1
```
`freeze_launcher.ps1` 会先跑 `make_diag_default.py` 生成 **gitignore** 的
`tools/launcher/dotabyss_diag_default.py`(`ENDPOINT_B64`=base64 端点),再以
`--hidden-import` 打进 exe。不设 env 则生成空串(不内建任何端点)。exe 在 `client/` 下本就忽略,密钥不进仓。

### 9.5 收取与清理
- 收日志:`bash /opt/dotabyss-diag/diag_fetch.sh [YYYY-MM-DD]`(列当日收件 + 抽崩溃签名);
  拉回本地 `scp -r server:/srv/diag-inbox/<日期> ./inbox-<日期>`。
- 定时清理:服务器 root crontab 已装「30 天保留 + 空目录回收 + 磁盘水位告警」。
