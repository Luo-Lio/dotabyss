## 2. 离线原理

游戏是 Unity IL2CPP + Addressables,DMM 平台登录。StoryViewer 插件(BepInEx + Harmony)做四件事:

1. **假 DMM 凭证**(`OfflineAuth`):跳过登录,直接进游戏。
2. **本机假 API 服务器**(`OfflineApi`,端口 18923):应答主数据与游戏 API 请求。
3. **资源重定向**(`RedirectAssetServer` + `ServeCachedBundles`):把 Addressables
   的 catalog/bundle 请求指到本机,由插件从客户端自带的 `_Data\Caches\<bundleName>\<hash>\__data`
   取用。
4. **本地内容**:剧情浏览 UI(F7)、剧情内跳过(F8)、解锁补丁(资料室全开放)、
   隐藏联网入口(商店/抽卡等)、错误弹窗与教学门禁的绕过。

**关键约束:未命中的 bundle 直接回 404,不回流官方 CDN。** 因此

- 离线包必须带**完整**缓存,不能做瘦身包;
- `Caches` 顶层条目数 < 10000 一律视为不完整(自检会红灯);
- 日志里出现 `→ 404` 行 = 有资源没命中缓存。

### 2.1 身份隔离(app.info)

- `ドットアビスX_Data\app.info` 两行:公司名 `EXNOA LLC.`、产品名 `ドットアビスX`。产品名会被
  **打包与修复改成 `ドットアビスX_offline`**,于是 LocalLow 存档、缓存、注册表与
  在线版完全分开(`LocalLow\EXNOA LLC_\ドットアビスX_offline\`),两边同时安装互不干扰。
- 备份 `app.info.bak_original` 只存在于开发机,**不进包**(打包会删掉)。
- 这是唯一允许修改的游戏本体文件;任何其它本体文件都必须走更新通道的 `client_body`。

### 2.2 catalog 与 LocalLow 播种(新机器首启的关键)

- 插件原本只从 `LocalLow\...\com.unity.addressables\*.bin` 读 catalog(取最近修改一份)。
  新机器 LocalLow 是空的 → 首启必失败。修法分三层:
  1. **包内种子**:`BepInEx\plugins\StoryViewer\catalog_seed\catalog_1.bin` + `.bin.hash`;
  2. **插件回退**(0.7.17 起):`ResolveCatalogFiles()` 优先种子目录,再回退 LocalLow;
  3. **启动器播种**:首次准备/修复/开始游戏前,把种子同步到
     `LocalLow\...\ドットアビスX_offline\com.unity.addressables\`(哈希一致则跳过)。
- `local_low_seed\AbsfRuntimeConfig.dat`:新机器存档目录缺该文件时补种(只补缺失、绝不覆盖)。
  它是游戏运行期写出的配置,缺省时游戏通常能自行重建,此播种是防御性措施。
- `local_low_seed\DownloadCache\*.dat`:`MasterDataStore.DownloadFirstAsync` 在线首下写出的
  主数据磁盘缓存(msgpack,含 m_buildings/m_characters/m_novel 等)。完整包仍从在线
  `LocalLow\EXNOA LLC_\ドットアビスX\DownloadCache` 原样带入,增量走 `master_data.zip`。
  **但这些 `.dat` 修不了 `MBuildings not found`**:MasterDataStore 是把表反序列化进**内存**后
  才可读,离线没有下载/清单管线去填内存,光把 `.dat` 放到磁盘目录不会被加载(新机模拟已证:
  文件与在线字节完全一致、内容含 m_buildings,进 Home 仍 not found)。`MBuildings not found`
  属离线固有、仅影响首页建筑渲染,剧情播出不依赖它;插件 0.7.26 起已移除误加的
  `SeedMasterDataIfNeeded`,并把该报错降级为单次友好提示,不再当作待修 bug。
- 更新通道也带 catalog(附件 `catalog_1.bin` + `.bin.hash`):启动器下载后写入包内种子
  目录,并立即重新播种 LocalLow。

`stories.json`(剧情索引)与 `previews/`(封面)是构建期从缓存导出、由插件读取的静态数据;
它们的格式与导出流程见仓库根 `README.md` 的导出工具一节。

- 索引内的中文(标题/角色/章节/简介)取自 AbyssMod 汉化缓存
  (`client\BepInEx\plugins\AbyssMod\cache\translations\`),**再由仓库内补充词典
  `tools/client-mod\i18n\story_zh_supplement.json` 同键覆盖**(由 `gen_stories_json.py` 合并;
  该文件缺失或损坏只提示、不改变旧行为)。新增角色/活动若缓存尚未收录,补这里即可。
- 注意 `home` 系列(首页「日常」)在游戏数据里**没有 `desc` 字段**,该系列本就没有简介
  (旧角色也一样),与翻译是否到位无关;要给它补简介需另开数据源或另行撰写。

### 2.3 Title ATT 旁路(全新机器卡在标题的真因,0.7.27 起)

- **症状**:机器冷启动卡在 Title(或更早卡在 `Boot`),进不了 Home;开发机与开发用虚拟机却“假通过”。
- **根因链**:`Project.AppEngine.OnServiceRegistered()` 内部执行
  `System.BitConverter.ToBoolean(byte[] value, int)` 且 `value == null` → 抛 `ArgumentNullException`
  → `Absf.Engine.InitializeServicesAsync` 中断 → 连 `Boot` 场景都出不去 → 场景管理器始终未就绪
  → 播放剧情时切场景挂死(黑屏)。`TopScene.ATTPermissionCheck →
  ATTManager.RequestAuthorizationAsync` 是同族的第二处。
- **一致变量是 Windows 版本(15 份玩家诊断包实测)**:11 份 **Windows 10** 包**全部**出现该 null 崩溃,
  4 份 **Windows 11** 包**全部**不出现(该判别量可由 `platform.release()` / `sys.getwindowsversion().build`
  得出,§9.1 已收进诊断摘要)。早先“开发机装过在线版、机器侧有缓存所以能过”的归因**不准确**:
  开发机同时满足“Win11”与“装过在线版”,而一台**从未装过在线版的干净 Win11 虚拟机同样正常**,
  等于把两个变量拆开 → 触发条件落在 **Windows 10**。
  **因此回归必须用 Windows 10 环境**;Win11 上永远复现不出来,不要拿“本机/VM 没事”当作“已修复”的证据。
- **修法**:`Patches\AttBypassPatch.cs` 用 Harmony Prefix 直接给 `ATTPermissionCheck` 返回
  一个**已完成的 `UniTask`**(`__result = UniTask.CompletedTask; return false;`),不让它去
  `await RequestAuthorizationAsync`;手法与已验证可用的 `DmmBypassPatch` 一致(不碰 async 状态机本身)。
  由配置 `BypassTitleAtt`(默认 **true**)门控;关闭时整类不安装、走游戏原逻辑。该键已列入
  `dotabyss_offline_core.py` 的 `OFFLINE_KEYS`,自检会校验、修复会强制写回 true。
- **插件本体的自包含**不依赖 Windows 注册表 / PlayerPrefs:靠
  `OfflineAuth`(硬编码假凭证)/ `ForceDmmSdkSuccess` / `OfflineApi` / `RedirectAssetServer` /
  `BootstrapAssets` / `SkipTutorial` + `DeployRuntimeConfigIfNeeded`(补 `AbsfRuntimeConfig.dat`)实现。
  `app.info` 改成 `*_offline` 只隔离了游戏自身的 LocalLow/注册表路径,**不覆盖 DMM SDK 自己读的那份
  机器侧数据**(它在 Win10 上为 null,归因见上一条),所以 ATT 必须单独旁路。
  (0.7.28 起的启动机器快照会**只读存在性**地探测 `HKCU\Software\EXNOA LLC.` 子键、不读任何值,见 §2.4。)
- **验证要点**:本机无法证伪旁路效果(开发机本就 ATT 能过、旁路不发光);**必须用 Win10
  fresh install 验证**。看两行日志即知是否装入:①`[Title ATT] 离线旁路:跳过 ATTPermissionCheck…`;
  ②§2.4 的 `[空字节兜底] BitConverter 保护已安装: N/3 目标`。
  **不要拿"Harmony 补丁安装完成: N 个"的数字当判据** —— 它会随版本变化,0.7.29 起还会因"目标缺失
  跳过"而变(0.7.25 是 30、0.7.27 是 31;0.7.29 曾把兜底从 3 类扩到 10 类,0.7.30 因互递归闪退
  回退为 3 类)。

### 2.4 BitConverter 空字节兜底(0.7.28 起;0.7.29 曾扩到 10 个重载,0.7.30 回退为 3 个)与启动机器快照

- **兜底补丁**(`Patches\NullByteGuardPatch.cs` + 目标表 `Patches\NullByteGuardTargets.cs`,
  配置 `GuardNullBitConverter`,默认 **true**):给 il2cpp 的 `System.BitConverter`(interop 类型
  `Il2CppSystem.BitConverter`)的 **3 个已知崩溃族重载**加 Harmony **Prefix** ——
  `ToBoolean / ToInt16 / ToInt32`;
  **仅当字节数组为 null** 时按该类型的默认值(`false`/`0`)返回并跳过原方法,非 null 时完全透传;
  每个重载命中时只记一次 `[空字节兜底] …` 日志。
  覆盖范围是一张**表**(单一事实来源):解析器按「方法名 + 返回类型 + 参数形状
  `(Il2CppStructArray<byte>[, int])`」定位。表里刻意**不收 `BitConverter.ToString`**:它返回字符串,
  且对空数组会合法地返回空串 —— 给它兜底是掩盖问题而不是修复。
- **为什么只有 3 个(0.7.29 的教训)**:0.7.29 曾把目标扩到全部 10 个「从字节数组读一个值」的重载
  (`ToBoolean / ToChar / ToInt16 / ToInt32 / ToInt64 / ToUInt16 / ToUInt32 / ToUInt64 / ToSingle / ToDouble`);
  实测对 `ToUInt32` 等目标安装 Harmony detour 会让托管代理与 `il2cpp_runtime_invoke` **无限互递归**
  → 栈溢出(`0xc00000fd`),玩家**打开剧情面板 / 播放剧情时游戏崩溃**。0.7.30 因此回退为
  `ToBoolean / ToInt16 / ToInt32` 这 3 个已知崩溃族;以后若要扩目标,必须先证明不会触发该互递归。
- **按 interop 实际暴露的重载安装**:不存在的重载走"按目标缺失跳过",**不能**让它走进 Harmony 安装
  (否则 `CreateClassProcessor().Patch()` 抛异常,被 `PatchManager` 记成「补丁 X 安装失败」的 Error,
  看起来像故障,反而淹没真正的失败)。因此 `PatchManager` 的跳过数文案是"按配置或目标缺失跳过"。
- **兜底覆盖自检(一眼可见)**:每次加载打印
  `[空字节兜底] BitConverter 保护已安装: N/3 目标(已覆盖: …)`;有未覆盖项时再列一行并注明
  "该 interop 未暴露该重载,该重载不受保护";**`ToBoolean/ToInt16/ToInt32` 这三个已知崩溃族缺失时
  该行升级为 Warning**(Win10 黑屏就是它们)。配置关闭时只打印一行说明后返回。
  该行同时含 `BitConverter` 与 `空字节兜底` 两个词,已被 §9.1 的关键字集收录 →
  **玩家诊断摘要里能直接看到**;这是判断"兜底到底装上没有"的第一手依据。
- **与 §2.3 的 `AttBypassPatch` / `EngineBootGuard` 互补,而且抗变化方向相反**:通用兜底按
  **方法形状**挂,不怕游戏侧方法改名/挪位(新本体新增的同类读取点会被同一个 Prefix 接住);
  ATT 旁路与 BootGuard 按**名字**挂,不怕读取换成别的重载。两者同时失配的概率因此很低。
- **明确不覆盖的边界(务必知道,别把它当根治)**:① 只兜「抛异常」这一种失败形态 —— 若新本体读到
  null 后**不抛而是走另一条分支**(例如判成未授权后卡住/黑屏),兜底不触发、日志里也不会留痕;
  ② 只覆盖上表 3 个重载,不给 `ToString`、`BinaryReader`、msgpack、直接取字节等其它读法兜底;
  ③ IL2CPP 若把 BCL 小方法**内联**进调用点,detour 不生效(不生效时不改变任何原有行为)。
  所以它仍是**尝试性修复**:把已知的一族症状变成"能继续走",不等于消除根因;根治方向是找到 Win10
  上为 null 的那份机器侧数据并主动供给(见 §8 与 `docs\日常更新流程.md` §7)。
- **启动机器快照**(`Plugin.LogMachineSnapshot()`,每次加载打印一次):`Application.platform` /
  `SystemInfo.operatingSystem` / `Environment.OSVersion.Version`(含 **build 号**,≥22000 即 Win11)/
  CPU / GPU / 内存,以及**仅存在性**探测:`%APPDATA%\dmmgameplayer5`、
  `%LOCALAPPDATA%\dmmgameplayer5-updater`、`LocalLow\EXNOA LLC_\ドットアビスX`(在线身份)、
  `..._offline`、`persistentDataPath\AbsfRuntimeConfig.dat`、`HKCU\Software\EXNOA LLC.`。
  **只判断存在性 / 目录条目数 / 子键名,绝不读取文件内容或注册表值**(DMM 登录态文件一律不碰)。
  目的是让玩家回传的 `LogOutput.log` 自带「Win10 还是 Win11、机器是否见过官方在线版」的判别信息。

## 3. 插件开发与部署

```powershell
# 编译 + 部署到 client\(版本号在 StoryViewer.csproj)
pwsh -File tools\client-mod\build.ps1

# 配置档:offline(默认)/ online-ref(在线抓包对照,需 VPN 与新鲜 DMM 凭证)

pwsh -File tools\client-mod\set-profile.ps1 offline
pwsh -File tools\client-mod\set-profile.ps1 online-ref
```

- 插件版本以 DLL 的 `ProductVersion` 为准(csproj `<Version>`);打包时会把配置头注释
  与 `offline_version.json` 一并刷成该版本。
- 玩家默认档在打包时生成:**离线键全为离线值**,并把 `LogPatches`/`SkipDebug` 关掉
  (`ErrorPopupLog` 保持开,便于支持)。

## 4. 启动器

- 源码:`tools/launcher/dotabyss_launcher.py`(tkinter,无第三方依赖)+ 共享逻辑
  `tools/launcher/dotabyss_offline_core.py`;配色取自游戏内 StoryViewer 面板,保持同一视觉风格。
- 冻结:`pwsh -File tools\launcher\freeze_launcher.ps1`
  - 先结束**同目录**残留的启动器进程(onefile 会留下子进程,持有 exe 会让 PyInstaller 报 WinError 5),
    再 PyInstaller onefile 到 `client\`,最后跑一次 `--smoke` 冒烟。
- 功能:开始游戏 / 更新 / 高级(自检 · 索引探针 · 修复 · 打开日志 · **离线更新包**)。
- 所有界面改动都经**队列**回主线程(`__BTN__` 改按钮文案、`__QUIT__` 关窗);
  后台线程不直接碰 Tk(踩过 Tcl_AsyncDelete 崩溃)。
- **首次准备**:`offline_version.json` 的 `first_ready=false` 时自动执行一次
  安全修复(解除 Zone.Identifier、重写离线配置、设置离线身份、播种 catalog/附属种子、
  归档超大日志)+ 全项自检,然后写 `first_ready=true`。
- **启动静默检查**:窗口起来后台经 GitHub CDN 查一次 latest 的 `version.json`
  (不消耗匿名 API 配额),只改按钮文案
  (「有更新」/「需重装」),不打扰、不阻塞。版本号相同也会按本地记录摘要和主数据种子
  做轻量就绪检查;缺失或不符时提示点「更新」补齐,不会扫描 430 MB 的本体/素材文件。
  顶栏只显示插件短版本,完整版本(含 source revision)写入启动日志。
- **更新顺序**(`_do_update`):基线门禁 → 安全修复 → `client_body` → `caches_added` →
  `master_data` → catalog → stories → previews → 插件 DLL → 玩家文档 → 启动器。
  **基线优先于版本号裁决**:基线不一致直接拒绝并要求重装完整包;版本号相同也会核对
  Release 已声明的产物,缺失或 MD5 不符时继续修复。
- **两条更新通道(`_do_update` 一个入口)**:①在线——主界「更新」经 GitHub CDN 取
  `version.json` 清单与资产(不走 REST API);②**离线更新包**——高级区按钮选一个本地 `.zip`,`_do_update_offline` 解压→
  `locate_release_pack_dir`/`parse_local_release` 读清单→`make_dir_fetchers(root)` 把
  `_http_get`/`_http_download` 换成本地取数器→调 `_do_update(parsed, remote)` 走**完全相同**的
  管道(基线/MD5 校验与回退均一致),finally 还原全局取数器并删临时目录;全程不联网。
  离线包就是 GitHub Release 那一整套资产打的 zip(由 `build_update_pack.py` 产出),两者内容一致。
- **自替换**:更新启动器本体时把新 exe 写成 `.new`,退出后由分离的 cmd 替换并重启。
  新脚本最长轮询约 60s 等文件解锁,**只有替换成功才 `start`**(失败追加写游戏根
  `launcher-error.log`),并在关闭前/启动期给出可见的「正在重启」提示——旧脚本重试窗口过短且
  替换失败仍无条件 `start`,正是「离线更新后窗口关闭、不自动重开」的根因。
  若上次替换没完成,启动时用 `pending_launcher_swap` 兜底(再点一次启动器即可完成)。
- **自测口**(开发用,不写进玩家文档):
  - `--release-dir <目录>`:把网络取数按 URL 末段文件名映射到本地发布目录(只认 `version.json`
    与各附件名,**不再需要 `release.json`**),用真实发布资产跑离线演练;
  - `--auto-update <输出文件>`:自动跑一次更新并把结果(`OK` / `OK-UPTODATE` /
    `BLOCKED-BASELINE` / `FAIL`)与日志尾巴写到文件;
  - `--smoke <输出文件>`:窗口起来即写 `PASS`。
- 单元测试:`test_offline_core.py`(118 项)、`test_launcher_update.py`(43 项)、
  `test_pack_tools.py`(11 项);另有布局回归 `test_launcher_layout.py`(需图形环境,
  通过时打印 `PASS launcher layout`)。

## 8. 已知坑与教训(务必遵守)

- **不要给高频方法挂 Harmony detour**,尤其参数里带 IL2CPP 对象/值类型状态机的
  (0.7.14 之前的致命 AV,随机崩溃;0.7.29 对 `BitConverter.ToUInt32` 等目标装 detour 会触发
  `il2cpp_runtime_invoke` 互递归栈溢出,0.7.30 已回退为 3 个目标 —— 见 §2.4)。F8 跳过现在的做法是:按键时
  `Resources.FindObjectsOfTypeAll` 实时找存活 `TopScene` 实例,直调 `OnSkipExec()`
  ——不打补丁、不缓存引用。
- `ViewerBehaviour` 的**实例方法里禁止捕获本地函数/`ref`/`out`**(IL2CPP 托管边界会炸);
  静态方法可以。
- AbyssMod 是另一个可能崩溃源。怀疑崩溃归属时,把 `StoryViewer.dll` 改名 `.bak`
  再跑一轮做隔离。
- **`cmd /c` 含引号路径的脚本必须用 `subprocess.Popen(script, shell=True)`**:
  argv 列表形式会被 Python 的 `list2cmdline` 把内层引号转义成 `\"`,cmd.exe 不认,
  替换脚本**静默失败**(2026-09-24 实测,启动器自替换因此卡住)。回归测试见
  `test_offline_core.py::LauncherReplaceCmdTest`。
- 后台线程禁止直接操作 Tk 控件(含 `root.after`);一律走队列,主线程处理。
  自测口同理(曾经的 Tcl_AsyncDelete 崩溃)。
- `check_health.bat` 里**不要用 `for %%F in ("%GAMEDIR%\*_Data\app.info")`**:
  cmd 的 `for` 不展开目录段通配;用先算好的 `DATADIR` 变量拼路径。
- 打包时 catalog 种子目录必须**先清空再写入且不写 `.bak_*`**,否则"无开发产物泄漏"
  校验会拦下(这是有意设计的守卫)。
- 控制台是 GBK,输出乱码先 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`。
- 工具里**不要启动游戏或 GUI 常驻程序**(会挂起);启动器冒烟/自测是短命进程,可以。
- `offline-api.log` 等运行期日志永远不进包(`*.log` 已在排除列表)。
- **Win11 上永远复现不出 Win10 的黑屏**:这台开发机同时满足"Win11"和"装过在线版",所以"本机没事"
  不能当验收 —— 2026-10-04~05 就是因此反复了三版(0.7.19 崩在 Boot → 0.7.22 抑制后崩在 Title →
  0.7.26 在 Title 撞第二处)。回归必须在 **Windows 10** 上做;没有 Win10 机器时至少灰度 1 个
  Win10 玩家,别直接全量。
- **判据是"初始化链走完 / 能播一篇",不是"日志里没有 Error"**:`EngineBootGuard` 用 Finalizer
  **吞掉**异常时,日志干净、流程也往前挪了一步(Boot→Title),但服务没注册成功、照样黑屏
  (0.7.22/0.7.26 的玩家包实测);只有让调用**成功返回**(0.7.27 的 ATT Prefix、0.7.28 的
  BitConverter Prefix)才真正修好。给这一类根因做兜底,优先选"让调用成功",不要选"抑制异常"。
- **崩溃随"本体"走,不随插件走**:0925 那一版在 Win10 上正常,是因为它跑的是 2026-09-30 之前的
  **旧本体**;本体换版后同一台 Win10 机器才会崩 —— 反证是同包版同插件在 Win11 上全程正常
  (15 份玩家诊断包:11 份 Win10 全部命中该 null 崩溃、4 份 Win11 全部不命中)。所以"官方更新本体"
  是这套离线版最大的外部风险面,同步更新时按 `docs\日常更新流程.md` §7 的清单走。

## 9. 诊断日志收集与回传(取证)

(`BepInEx\LogOutput.log`、`offline-api.log`),启动器负责**收集→打包→上传**。

### 9.1 客户端(`tools/launcher/dotabyss_offline_core.py`)
- `collect_diagnostics(game_dir)`:收集日志与环境信息,产出 `diagnostics\dotabyss-diag-<时间>.zip`。
  超大日志保留**头 2MB + 尾**(带截断标记,开机崩溃签名不被裁掉);并从开机段抽**「崩溃签名」**
  (`aa/runtime.json`、`TextDataProvider`、`BitConverter`、`InitializeAsync`、`场景切换`、
  `[空字节兜底]` 覆盖行等)写进 `diag_summary.txt`,免解压即可一眼定位。
  其中 `[空字节兜底] BitConverter 保护已安装: N/3 目标` 一行同时含 `BitConverter` 与
  `空字节兜底`(`DIAG_SIGNATURE_PATTERNS` 已含前者),可直接用来判断兜底是否装上。
- **诊断包内容清单**(`zip 内路径` ← 来源):`diag/diag_summary.txt`(摘要:离线包版本/app.info/
  配置离线档与 DiagAssets·ApiPort/Caches 目录数与字节/资源命中统计/health_check/index_probe/崩溃签名)、
  **`机器信息`**(`platform.*`、**Windows 构建号与「是否 Win11(build≥22000)」**、Python/区域、
  CPU 逻辑核数、物理内存)、**`机器侧状态(路径探测,仅元数据)`**(在线/离线身份目录、DMM Game Player
  目录、DMM 更新器的**存在性与顶层条目数**;`HKCU\Software\EXNOA LLC.` 的**子键名**;
  `AbsfRuntimeConfig.dat` 的存在性与大小)、`diag/logs/*`(BepInEx 下 `LogOutput.log` 等日志)、
  `diag/config/*.cfg`(BepInEx\config 全部)、`diag/offline_version.json`、`diag/app.info`、
  `diag/launcher.json`(仅 `github_repo`)、`diag/plugin/stories.json`。
  **故意不含**:服务器端点(IP/令牌/隐身路径只内建在 exe 里、不进包也不进摘要)、游戏存档、玩家隐私文件。
  机器侧状态一段**只做存在性元数据**:绝不读取/收集 `%APPDATA%\dmmgameplayer5` 里
  `authAccessTokenData.enc`/`dmmgame.cnf`/`dmmgameuser.cnf` 等 DMM 登录态文件的内容,注册表只列子键名不读值。
- `upload_diagnostics(game_dir, zip)`:POST `multipart/form-data`,字段 `file`=zip、`summary`=摘要纯文本;
  返回 `skipped/ok/error`。**未配端点时只保留本地 zip 并跳过,绝不猜端点。**
- 端点解析优先级(`_diag_upload_target`):环境变量 `DOTABYSS_DIAG_UPLOAD_URL`/`_TOKEN`
  → `launcher.json` 明文 `diag_upload_url`/`diag_upload_token` → 隐身字段 **`diag_endpoint`**
  (base64 的 `url\ntoken`,由 `_diag_encode_endpoint`/`_diag_decode_endpoint` 编解码)
