# ゲーム更新后的离线包日常更新流程

> **适用**:官方更新(客户端本体 / 素材 / 新剧情)后,把离线包更新到最新并发布 GitHub Release。
> **配套文档**:[`离线版实现说明_开发者必读.md`](离线版实现说明_开发者必读.md)(离线原理、打包与校验)、
> [`GitHub更新流程.md`](GitHub更新流程.md)(更新通道机制、`version.json` 字段、回滚)。
> 打日更包时**按本表勾,不要凭记忆**。

## 1. 角色与路径

| 路径 | 角色 |

## 2. 一图流

```
⓪ 确认「旧完整包」基座完好(没被重打覆盖;否则先从完整包 zip 还原,见 §10)
   → ① 游戏更新完、缓存稳定;确认新内容已真正下载(见 §10.3)
   → ② robocopy 本体+缓存 同步 game→client(排除 app.info / BepInEx)
   → ③ 更新 client 的 catalog 种子(取「在线身份」目录里最新一份!)
   → ④ tools.export 增量导出(刷新 manifest/封面/剧情索引)
   → ⑤ 重建 stories.json 并部署到 client + 重生成 previews(核对角色/剧情数已含新内容)
   → ⑥ build_github_pack(以 client 为源,旧完整包作 --caches-since)
   → ⑦ 校验 md5/清单 + 离线演练三态
   → ⑧ 提交源码变更(如有)→ ⑨ gh release create → ⑩ 匿名复核
```

> 与"完整包"的关系:本流程只产出**增量更新附件**(老玩家走启动器「更新」)。
> **新玩家**用的 8 GB 完整包是另一条路径,见 §9。

## 3. 前置条件(缺一不可)

- [ ] **游戏与启动器均已退出**(`Get-Process | ? ProcessName -match 'ドットアビスX|Dotabyss'` 为空)。
- [ ] **游戏已下载完毕**:`Caches` 顶层目录数**间隔十几秒连测两次相同**(更新期数字会一直涨)。
- [ ] **仓库非空**:GitHub **不能在空仓库上发 Release**(报 `Repository is empty`)。
      首次需先有一次提交并推送(见 §8)。
- [ ] `gh auth status` 显示 `Luo-Lio` 为 active。
- [ ] **旧完整包基座可用**:`--caches-since` 指向的目录必须仍是「玩家手上那一版」的内容;
      若它已被重打覆盖,先按 §10 从完整包 zip 还原,否则老玩家会漏掉整批素材。
- [ ] 未换基线(见 §7);若要换基线,先按 §9 重打完整包。

## 4. 分步操作

> 以下命令默认在**仓库根目录**(`<repo>`,即含 `tools\` 的那一级)执行;路径按需替换。

### ① 预检:单元测试(基线必须全绿)

```powershell
D:\Python\python.exe tools\launcher\test_offline_core.py      # 107 项
D:\Python\python.exe tools\launcher\test_launcher_update.py   # 24 项
D:\Python\python.exe tools\launcher\test_pack_tools.py        # 11 项
```

### ② 同步 game → client(本体 + 缓存,增量)

先 `/L` 预演看体量(应为几百 MB,主要来自本体大文件;**绝不是 8 GB**):

```powershell
robocopy "E:\dmm\dotabyss_x_cl" "<repo>\client" /E /L /MT:16 /R:2 /W:2 /NP `
  /XD "E:\dmm\dotabyss_x_cl\BepInEx" /XF "app.info" "app.info.bak_original" "*.log" "*.bak*" "*.new"
```

确认无误后去掉 `/L` 正式执行(退出码 `<8` 均正常,`3` = 已复制且有 extras):

```powershell
robocopy "E:\dmm\dotabyss_x_cl" "<repo>\client" /E /MT:16 /R:2 /W:2 /NP `
  /XD "E:\dmm\dotabyss_x_cl\BepInEx" /XF "app.info" "app.info.bak_original" "*.log" "*.bak*" "*.new"
```

同步后核对:

```powershell
(Get-ChildItem "<repo>\client\ドットアビスX_Data\Caches").Count      # 应 == 在线机数量
Get-Content "<repo>\client\ドットアビスX_Data\app.info"             # 必须仍是 ドットアビスX_offline
```

- **`BepInEx` 整个排除**:client 的插件/配置/interop 是精心维护的,`AbyssMod` 汉化缓存按需另同步(见注)。
- **`app.info` 必须排除**:它是离线身份(`_offline` 后缀),被在线版覆盖会让存档/缓存目录跑回官方那份。
- `AbyssMod` 汉化缓存只在 `static/names` 变化时才需要同步(`gen_stories_json.py` 用它查中文标题);
  多数更新里它不变,可用 `Get-FileHash` 比对后再决定。

### ③ 更新 catalog 种子(最容易踩的坑)

> ⚠️ `core.source_catalog_pair()` 会**优先返回离线身份目录**(`…_offline\…`),那里通常是旧 catalog,
> 于是自动取源会拿到**过期**的一份。日更必须**显式取在线身份目录里最新的一份**。

```powershell
$online = "$env:USERPROFILE\AppData\LocalLow\EXNOA LLC_\ドットアビスX\com.unity.addressables"
Get-ChildItem $online -Filter *.bin | Sort-Object LastWriteTime -Descending | Select-Object -First 1

D:\Python\python.exe -c "import sys; sys.path.insert(0, r'tools\launcher'); import dotabyss_offline_core as core; b, h = core.newest_catalog_pair(r'$online'); print(b); print('hash =', core.catalog_hash_text(h)); print(core.write_catalog_seed(r'<repo>\client', b, h, backup=False))"
```

- 校验:写入后 `client\BepInEx\plugins\StoryViewer\catalog_seed\catalog_1.bin.hash` 的内容
  **应等于**在线目录最新 `*.hash` 的内容(32 字符)。
- 若改用完整包流程,可用 `build_full_pack.py --catalog-bin <在线最新.bin>` 显式指定,绕过上面的坑。

### ④ 增量导出

```powershell
D:\Python\python.exe -m tools.export
```

- 读**在线身份** LocalLow 的最新 catalog 与 master data;已导出项会跳过。
- 关注输出:`导出 N 个`(本次新增)、`失败 0`、`剧情索引 … 条`、动态素材统计。
- 失败非 0 要查 `output/manifest.json` 的 `failures` 再决定是否放行。

### ⑤ 重建剧情索引与封面

```powershell
D:\Python\python.exe tools\client-mod\gen_stories_json.py
Copy-Item tools\client-mod\StoryViewer\stories.json "<repo>\client\BepInEx\plugins\StoryViewer\stories.json" -Force
D:\Python\python.exe tools\client-mod\gen_covers.py
```

- **顺序不能反**:`gen_covers.py` 读的是 `client` 里的 `stories.json`,所以**先部署再生成封面**。
- 上新内容时用 JSON 对比新增 key,确认与本次更新吻合:

```powershell
D:\Python\python.exe -c "import json; old=json.load(open(r'dist\ドットアビスX离线版\BepInEx\plugins\StoryViewer\stories.json',encoding='utf-8')); new=json.load(open(r'client\BepInEx\plugins\StoryViewer\stories.json',encoding='utf-8')); a={s['k'] for s in old['stories']}; b={s['k'] for s in new['stories']}; print('added', sorted(b-a)); print('removed', sorted(a-b))"
```

### ⑥ 生成发布附件

以 **`client` 为打包源**、**旧完整包为素材增量基座**(不重打 8 GB 完整包的标准做法):

```powershell
D:\Python\python.exe tools\launcher\build_github_pack.py --pack "<repo>\client" `
  --version <YYYYMMDD> --baseline <基线,如 20260924> --channel baseline `
  --notes "更新说明" --caches-since "<repo>\dist\ドットアビスX离线版"
```

- `--pack client` 时 client 内没有 `offline_version.json`,所以**必须显式给 `--baseline`/`--channel`**;
  会打印一条 `[warn] 版本号与完整包不一致` —— **属预期**,不是错误。
- 产出 `dist\release_<版本>\`:`version.json / StoryViewer.dll / stories.json /
  DotabyssOfflineLauncher.exe / previews.zip / player_docs.zip / catalog_1.bin(+.hash) /
  client_body.zip / caches_update.zip`(无素材增量时不产 `caches_update.zip`)。
- **附件名大小写敏感**,启动器按固定名识别;缺哪个跳哪步,但"声明了内容却缺附件"会失败关闭。

### ⑦ 发布前校验(硬门槛)

1. **逐项 md5**:`version.json` 里每个 md5 与该附件实际 md5 一致;`catalog_hash` 与
   `client` 的 `catalog_1.bin.hash` 内容一致。
2. **清单逐文件对拍**:`client_body.files`(路径→md5)与 `caches_added.files` 里每一项,
   在 `client` 下都存在且 md5 相同;且 `client_body_todo == 0`、`caches_added_todo == 0`。
3. **离线演练**(无需真实网络):建一个假发布目录(把 `release_<版本>\` 拷一份进去,
   另写 `release.json` = GitHub API 返回体:`{"tag_name":…,"assets":[{"name":…,"browser_download_url":"…/<文件名>"}…]}`),
   再对一个"旧包目录"跑真实启动器:

   ```powershell
   DotabyssOfflineLauncher.exe --game-dir <旧包目录> --release-dir <假发布目录> --auto-update out.txt
   ```

   期望(用启动器自带的 exe 跑):
   - 首次:`OK version=<新版本>`(日志按 本体→素材→catalog→索引→封面→DLL→文档→启动器 顺序);
   - 再跑一次:`OK-UPTODATE`;
   - 把假发布目录 `version.json` 的 `baseline` 改掉再跑:`BLOCKED-BASELINE`,且包内版本文件不变。

   > 假游戏目录做最小集即可:`_Data\app.info`(离线身份)、`launcher.json`、旧
   > `BepInEx\plugins\StoryViewer\offline_version.json`(基线要一致)、插件配置、
   > `catalog_seed\`、`DotabyssOfflineLauncher.exe`。

### ⑧ 提交源码变更(仅在改了源码/文档时)

完整包、client、dist 均不入库;只提交 `README.md`、`.gitignore`、`docs/`、`mockups/`、`tools/`。

```powershell
git add -A
git status --short          # 确认没有 client/ dist/ output/ bin/ obj/ 混入
git commit -m "<说明>"
git push origin main
```

- `bin/`、`obj/`(以及 `__pycache__/`)已在 `.gitignore` 里,不要提交构建产物。
- 只发 Release 而不改源码时,可跳过本步。

### ⑨ 发布

```powershell
gh release create <YYYYMMDD> --repo Luo-Lio/dotabyss `
  --title "离线包 <YYYYMMDD>" --notes-file <说明文件> "dist\release_<YYYYMMDD>\*"
```

- `gh release create` 会把该 Release 设为 **latest**(非草稿、非预发布)。
- 空仓库会报 `Repository is empty`,先完成 §8 的一次推送。

### ⑩ 发布后匿名复核

```powershell
gh api repos/Luo-Lio/dotabyss/releases/latest --jq '.tag_name, (.assets|length)'

D:\Python\python.exe -c "import urllib.request,hashlib; raw=urllib.request.urlopen(urllib.request.Request('https://github.com/Luo-Lio/dotabyss/releases/download/<版本>/version.json',headers={'User-Agent':'verify'}),timeout=30).read(); print(hashlib.md5(raw).hexdigest())"
```

- `latest` == 新版本号;附件数/体积与本地逐一对上;`version.json` 匿名下载 md5 == 本地 md5。
- 最后用**旧版离线包**点一次启动器「更新」,实机确认:开列表(F7)→ 播新剧情 → 跳过(F8)正常,
  且 `LogOutput.log` 无 `404` / `STRICT-MISS` / patch 失败。

## 5. 常见坑(实测)

| 坑 | 症状 / 根因 | 规避 |
| --- | --- | --- |
| 游戏还在下载就同步 | 包内素材不全,实机 404/黑屏 | 同步前 `Caches` 计数连测两次一致 |
| catalog 取到旧的 | `source_catalog_pair` 优先离线身份目录(滞后)→ 新 bundle 找不到 | 显式取**在线身份**目录最新 `*.bin`(§③) |
| `app.info` 被覆盖 | 数据目录变回在线版,玩家存档错位 | 同步 `/XF app.info`;务必复核仍为 `_offline` |
| 覆盖了 `BepInEx` | 插件/配置/interop 被在线机版本替换 | 同步 `/XD …\BepInEx` |
| `stories.json` 与封面顺序反了 | 封面按旧索引生成,新剧情没封面 | 先部署 `stories.json` 再 `gen_covers.py` |
| 同版本号重发 | 启动器判"已是最新",玩家不下(撤下后再用同号也一样,已更过的玩家拿不到修订内容) | 一律换**递增日期**版本号;不要同号重发 |
| **旧完整包被重打覆盖** | `--caches-since` 基座变成新版内容 → 增量只含最后一点,老玩家**漏掉整批素材**(实机 404) | 重打前把旧包改名保留;已覆盖则从完整包 zip 还原基座(§10.2) |
| 游戏没下载新内容就出包 | master data 已认识新角色,但 Caches 里没有其 bundle → 导出跳过,`stories.json` 整组缺该角色 | 出包前核对(§10.3);在游戏内触发下载后再同步 |
| 拿没重新同步的 `client` 出包 | `client` 还是上一版内容,新角色/新剧情进不了包 | 出包前确认 `client` 的 Caches 计数 == 在线机 |
| 空仓库发 Release | `HTTP 422 Repository is empty` | 先有首个提交并推送 |
| 提交进构建产物 | `bin/`、`obj/`、缓存被入库 | 已 gitignore;`git add` 后复查 `git status` |
| 素材增量变很大 | 单附件接近/超过 2 GB | 改走新完整包路线(§9) |

## 6. 版本号与基线

- 版本号 = **日期 `YYYYMMDD`**,必须比上一次发布**大**;内容有改动也必须递增(同号 = 已是最新)。
- `baseline` 是**冻结的完整包日期**:同一代基线内**不要改**;改了等于要求所有老玩家重装。
- 附件 size 上限:GitHub 单附件 2 GB。`client_body.zip` 约 180 MB、`caches_update.zip` 通常几十 MB,
  正常;若素材增量逼近 2 GB,说明该重打完整包。

## 7. 插件 / 启动器有变更时的额外步骤(本次未涉及)

```powershell
# 改了插件源码:编译 + 部署到 client(同时复制 stories.json)
pwsh -File tools\client-mod\build.ps1

# 改了启动器源码:重新冻结到 client(含 --smoke 冒烟)
pwsh -File tools\launcher\freeze_launcher.ps1
```

- 插件版本以 DLL 的 `ProductVersion` 为准(`StoryViewer.csproj` 的 `<Version>`)。
- 改过插件后:补跑 PatchCheck / SkipTest(见 `离线版实现说明_开发者必读.md` §6),
  并按需提高 `<Version>`。

> **注意**:官方更新若改了 `GameAssembly.dll`,**现有插件不一定仍适配**新本体。
> 本流程不会自动重编译插件;发布后务必按 §⑩ 实机验证补丁是否仍生效。

## 8. 首次/异常情况

- **仓库为空**:先按 §8 建首个提交并 `git push -u origin main`(本地分支若为 `master`,可
  `git branch -m main` 对齐远端默认分支)。
- **换基线**(游戏大版本 / 缓存结构变化 / 需重发整包):用新的 `baseline` 重打完整包并在 Release 同步该 `baseline`,
  老玩家会被提示重装。
- **回滚**:玩家侧删 `BepInEx\plugins\StoryViewer\offline_version.json` 后重解压完整包;
  维护侧发一个版本号更高的旧内容 Release(不要同号重发)。

## 9. 新玩家完整包(与增量发布是两条路)

需要给新玩家一次性整包时(选做):

```powershell
D:\Python\python.exe tools\launcher\build_full_pack.py --recopy --zip --repo Luo-Lio/dotabyss
```

- 产出 `dist\ドットアビスX离线版\` 与 `dist\ドットアビスX离线版_<版本>.zip`(约 8 GB,超 GitHub 附件上限,走网盘)。
- 它同时刷新包内 `offline_version.json`、`launcher.json`、离线身份、`catalog_seed\`、`local_low_seed\`,
  并做全套校验(缓存条目、previews、无开发产物泄漏等),校验不过会 `[ABORT]` —— **不要交付未过校验的目录**。
- 重打前建议把旧包**改名留存**(如 `dist\ドットアビスX离线版_<旧版本>`),它仍是下次增量的比对基座。
- 重打后:新玩家的起点(`version`)应 ≤ 最新 Release 的版本号,否则更新按钮会显示"已是最新"。

## 10. 基座与内容完整性(2026-10-01 实战补充)

### 10.1 基座为什么会失效

`--caches-since` 的比对口径是:包内 `_Data/Caches` 里**路径不在旧包(或大小不同)**的文件。
旧包 = **玩家手上那一份**;而重打完整包(`build_full_pack --recopy`)会**原地覆盖**
`dist\ドットアビスX离线版\`。一旦被覆盖,基座就变成新版内容,增量会塌缩成"只差最后一点",
老玩家会**整批漏掉素材**(切到新内容时实机 404)。

- ✅ 正确做法:重打前把旧包**改名保留**,如 `dist\ドットアビスX离线版(旧)`,再用
  `--caches-since "dist\ドットアビスX离线版(旧)"`。
- ⚠️ 症状识别:增量 zip 明显偏小、或 `caches_added` 只有寥寥几十个 bundle,而本次明明有
  新角色/新活动素材 —— **先怀疑基座**。
- 🔎 自检:把 `Caches` 目录数与旧包对拍。实战:基座(0925 包)= 21812 cdn、
  当时 `client` = 21852,则增量应恰好是 **46 cdn**;若算出 **0**,就是基座被覆盖了。

### 10.2 基座被覆盖后怎么还原

只要该版本的**完整包 zip 还在**,就能还原基座。zip 内条目带一层 `ドットアビスX离线版/`
前缀;比对只看**路径 + 大小**,所以只需解出 `_Data/Caches` 子树:

```python
# 解到 dist\_base_<版本>\(实测 43833 文件 / 约 7.5 GB,~35 秒)
import os, shutil, zipfile
R = r"E:\agent\dmm\dotabyss"
ZIP = os.path.join(R, "dist", "ドットアビスX离线版_20260925.zip")
PRE = "ドットアビスX离线版/ドットアビスX_Data/Caches/"
OUT = os.path.join(R, "dist", "_base_20260925", "ドットアビスX_Data", "Caches")
with zipfile.ZipFile(ZIP) as z:
    for i in z.infolist():
        n = i.filename.replace("\\", "/")
        if not n.startswith(PRE) or n.endswith("/"):
            continue
        dest = os.path.join(OUT, *n[len(PRE):].split("/"))
        os.makedirs(os.path.dirname(dest), exist_ok=True)
        with z.open(i) as s, open(dest, "wb") as d:
            shutil.copyfileobj(s, d, 1 << 20)
```

- 然后把 `--caches-since` 指向 `dist\_base_<版本>`。
- 该目录只是"比对用的基座",**不是可分发的完整包**;出完包可删(需要时再解一次)。

### 10.3 新角色 / 新内容是否真的被游戏下载了

「master data 认识」≠「素材已在本地」。master data 会**先于**素材出现,导致导出静默缺内容:

- **找出今天的角色**:master data `m_characters` 每行的**最后一列是实装时间**
  (如 `2026-09-30 13:00:00`)。按它倒序即得新增角色。
  实战:`パウリーナ`(1300028)、`オーレリナ`(1300036) 为 2026-09-30 新增。
- **判断素材是否到齐**:该角色的 bundle 在 catalog 里有,但 `Caches` 下**没有对应 cdn 目录**
  → 游戏还没下。导出侧表现:`manifest.stories.characters` 有该角色,
  但 `stories.json` 里没有 → 就是没下到(缺 bundle → 该角色整组被跳过)。
- **触发下载**:在游戏内进入该角色 / 该剧情界面(或用游戏的「一括ダウンロード」),
  等 `Caches` 目录数**明显上涨**(实战:21853 → 22506,新增约 650 个 cdn)。
- 出包前顺手核对:`client` 的 Caches 计数 == 在线机;`stories.json` 的角色数 == master data 角色数。

### 10.4 撤下 / 重发

- 撤下:`gh release delete <版本> --repo Luo-Lio/dotabyss --yes`(默认**保留 tag**)。
- 已撤下的内容如需重新发布,**必须换更高的版本号**(已更过旧号的玩家不会被判定为有新版本)。
- 撤下到重发之间 `releases/latest` 会 404;启动器的更新检查对此是**静默跳过**(不报错)。
